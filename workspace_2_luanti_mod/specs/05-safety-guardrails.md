# ws2-05-safety-guardrails: Защита Рантайма и Механизмы Очередей

> **ABSTRACT:** Спецификация описывает подсистему `command_queue`. Документ регламентирует механизмы защиты Главного Потока (Main Thread) от блокировок и исчерпания памяти (OOM) через строгие лимиты исполнения команд (Rate Limiting) и нарезку тяжелых операций на чанки (Time Slicing).

## 1. Per-Plot Command Queues (Изолированные очереди)

Для предотвращения влияния одного клиента на работу других (Noisy Neighbor Problem), подсистема `SHALL` поддерживать изолированную очередь (FIFO buffer) для каждого активного Участка (`plot_id`).

* КОГДА подсистема `[[ws2-02-network-ingress]]` валидирует входящий JSON, она `SHALL NOT` исполнять его немедленно. Вместо этого команда `SHALL` добавляться в конец очереди соответствующего `plot_id`.
* Очереди `SHALL` храниться в оперативной памяти (In-Memory Lua Tables).

## 2. Tick-based Rate Limiting (Лимиты Исполнения)

Подсистема `SHALL` дозировать нагрузку на движок, обрабатывая очереди строго в рамках хука `globalstep`.

* На каждом серверном тике подсистема `SHALL` итерироваться по всем активным очередям Участков.
* Для каждого Участка подсистема `SHALL` извлечь и исполнить **не более `MAX_ACTIONS_PER_TICK` команд** (по умолчанию `10`).
* ЕСЛИ очередь Участка содержит больше команд, оставшиеся команды `SHALL` быть отложены до следующего вызова `globalstep`.
* После выполнения команды подсистема `SHALL` немедленно сформировать JSON-ответ и передать его в сетевой слой для отправки клиенту.

## 3. Time Slicing (Защита от тяжелых операций)

Команда `bulk_set_nodes` (Массовая застройка) представляет критическую угрозу для стабильности TPS (Ticks Per Second) сервера. ИИ-агент `SHALL` реализовать для неё паттерн Time Slicing.

* КОГДА из очереди извлекается команда `bulk_set_nodes` с массивом из $N$ блоков, подсистема `SHALL` разбить этот массив на чанки (фрагменты) размером **не более `MAX_BLOCKS_PER_SLICE`** (по умолчанию `500` блоков).
* Подсистема `SHALL` применить физическую установку (`minetest.set_node`) только для первого чанка в текущем тике.
* Оставшиеся чанки `SHALL` быть сохранены в скрытую системную микро-очередь Участка и `SHALL` применяться по одному чанку на каждый последующий `globalstep`.
* **Asynchronous Acknowledgment:** Подсистема `SHALL` отправить ответ `{"status": "ok", "data": {"success": true, "blocks_queued": N}}` немедленно после разбивки на чанки, НЕ дожидаясь фактической физической установки всех блоков.

## 4. Queue Flushing (Очистка очередей)

Для защиты от зависания алгоритмов при обрыве связи ("Zombie Connections"), подсистема `SHALL` поддерживать мгновенную очистку состояний.

* КОГДА `[[ws2-02-network-ingress]]` регистрирует потерю TCP-соединения для `plot_id`, он `SHALL` вызвать триггер очистки.
* Триггер `SHALL` немедленно удалить очередь команд данного Участка из памяти и остановить все фоновые процессы Time Slicing (например, недостроенные массивы `bulk_set_nodes` `SHALL` быть отброшены).
